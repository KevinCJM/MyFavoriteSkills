# v2.2.0：编程四问融入说明

本次需求是在 v2.1.0 的现有派工与验收 Skill 中贯穿用户的编程原则。不新增 MCP 能力、调度
服务或模型路由，不改变 `ocw/1` 格式和现有辅助脚本接口。规则来源是本次用户明确要求；历史
开源研究留作追溯，不把其美化或降债建议当成当前改动授权。

## 原则原文与执行含义

禁止为了追求代码简洁优雅而修改代码；禁止为了解决原代码技术债而修改代码；禁止主动修复
自认为的额外 BUG。在详细设计中，逐个独立改动回答：

1. **是否属于当前需求？** 不属于，不改；必须关联真实需求，不能反过来编 AC 给额外修改找理由。
2. **不改是否阻塞？** 不阻塞，不改；阻塞是当前结果或必要验证无法完成，不是以后不够好维护。
3. **是否可以最小改造？** 只解决当前障碍，最小化正确改动及影响；不按行数多少选方案。
4. **是否影响原有契约？** 保留 API、配置、日志、数据结构、下游依赖、用户工作流及兼容逻辑。
   不确定或有冲突时先停相关改动；Codex 不可自行豁免。用户已明确授权的具体契约变化应准确
   记录为新需求边界，不重复询问，也不将其泛化成其他变化的授权。

## 融入的位置

| 阶段 | 新要求 |
|---|---|
| Codex 直接改动 | 微小改动也经过四问，但不强迫创建文档或启动 Worker。 |
| 详细设计 / Designer | 每个独立改动给出四问依据，标为可实施、不改或阻塞；不只给整个功能四个“是”。 |
| 派工 / Builder | 普通低风险任务用一行 Boundary 概括四问；复杂/高风险任务才维护 C-ID 四问表；Worker 可在已准入边界内选择必要的局部实现。 |
| Scout | 只调查所问问题；发现额外疑似 BUG，不顺手改、不扩成全库技术债清单。 |
| 自审核 / Verifier | 查实际 diff 是否每项都有必要性；不能把风格、旧债或无关旧 BUG 变成必须返工。 |
| 增量返工 | 引用原 C-ID/F-ID，只补本轮变化的答案；评审建议不自动扩大授权。 |
| 多 Worker / 集成 | 共享同一总体需求边界；解决冲突、共享接口和锁文件也要通过四问。 |
| 最终验收 | 检查是否多改、是否破坏契约、证据是否对应当前状态；绿色测试不能抵消无授权改动。 |

## 关键边界

**复用不是目的。** 已有逻辑能直接完成当前需求时优先复用；不能为了“统一复用”更改其他调用方。

**最小不是掩盖症状。** 需要满足整个当前要求及必要边界行为，不能为了小 diff 留下当前缺陷。

**本次新问题与旧问题分开。** 本次引入的缺陷或多余修改要修复/撤除；无关旧问题不擅自修。
已有问题确实阻塞当前需求时，报告证据和最小选项，不因为“阻塞”就自动获得越界权。
重大安全或数据丢失风险要如实报告，必要时停止危险执行，但仍不自行扩大修复范围。

**文件边界不等于行为授权。** 可以修改 `foo.py`，不代表能清理其中所有函数。Reviewer 也必须
给出当前需求、引入缺陷、相关契约或必要验证缺口的依据，不能因个人风格偏好要求返工。

**契约影响不能只写“没有”。** 检查相关参数/返回/错误类型、默认值/配置优先级、日志消费者、
数据类型/顺序/单位/空值、下游调用、副作用和用户流程。只核查相关面，不重复审计整个项目。

## 提示词与 Token

- 完整任务把四问表放进 `Decisions` 或引用双方可读的权威设计。
- 紧凑任务在 `Scope` 放一行 `Boundary:` 四问摘要，不创建 C-ID 表或 ledger。
- 返工在 `Correction` 仅更新受影响行；报告和台账引用，不重复抄写。
- 每个独立行为/验证改动一行，不是每行源码一行，也不是每个 Worker 重写全部需求。
- 不增加“先确认收到”的模型往返；已知非必要改动直接不做。

现有 `prompt_contract.py` 只检查结构，**不验证四问是否真实成立，也不强制检查四问是否填写**；
`scope_only_pass` 也不证明路径内的每个修改合理。不新增形式上通过就算批准的语义检查器。
