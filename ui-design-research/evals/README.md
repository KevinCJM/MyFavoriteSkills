# Skill 回归评测

维护 Skill 时按需执行；普通 UI 任务不加载这里。这里是可复跑的输入与判定标准，不是已通过的模型测试报告，也不是客户端会自动执行的评测配置。

- [trigger-cases.yaml](trigger-cases.yaml)：隐式选择的正例、反例及边界。
- [behavior-cases.yaml](behavior-cases.yaml)：显式调用后的行为、证据和范围检查。

`schema_version: 1` 是本包的用例格式，不是 Agent Skills 标准字段。YAML 可由自己的执行器读取，也可逐条手工执行；本包不启动模型、不安装依赖、不写全局配置。

## 触发测试

1. 在隔离的新会话里启用该 Skill 的正常发现，记录宿主、模型、Skill 提交/哈希及同时可见的其他 Skills。
2. 只提交用例的 `prompt`，按 `context` 准备项目背景；不要显式点名 Skill，也不要提前把 SKILL.md 正文放进上下文。
3. 观察实际技能选择或文件读取记录，与 `expected_trigger` 比较。模型口头说“我会使用”不能单独证明已加载。
4. 正例未选中记漏触发，反例被选中记误触发；看不到宿主路由证据时记 `unobservable`，不要猜测。

触发依赖宿主发现和模型选择。一次运行只说明该次结果；需要评估稳定性时复跑，并分别统计正反例，不用少量样本宣称普遍准确率。

## 行为测试

为所选用例准备独立项目副本或相应背景，提供 `context` 和 `prompt`，显式加载当前版本 Skill。`required_observations` 和 `failure_signals` 只给评估者，不放入被测提示。

`context` 中的工具条件须由执行环境真实控制；例如“无浏览器”应禁用相关能力，不能只让模型假装没有。涉及代码实现的用例需要实际可运行的项目，不能用一段背景叙述代替实现证据。没有对应环境记 `not_run`。

核对最终回答、工具轨迹和文件 diff：相关材料是否按需读取，是否保留项目技术栈，是否在授权范围内行动，证据表述是否与操作相符。只有结果满足所列观察项且无失败信号，才记该次 `pass`；无法判断记 `inconclusive`。

## 记录结果

记录 `case_id`、Skill 提交/哈希、日期、宿主/模型、环境与工具、运行次数、`pass/fail/not_run/unobservable/inconclusive`、轨迹/产物位置及判定理由。产物保存在测试工作区；发布记录前去掉私有项目内容、凭据和无关日志。

YAML 解析、文档链接检查、用例静态走查与真实模型执行分别报告。更新指令后先复跑受影响用例，不把“新增了用例”写成“模型评测通过”。
