# 调研输出与设计交接

先适配用户要求的详略。通常一个推荐、少量具体链接和适配点就足够。
此文件规定信息内容，不强制每次使用相同标题、表格或字段。

## 简洁调研

1. **建议**：选择什么，解决哪个问题，是否保留当前组件体系。
2. **依据**：具体组件/页面链接，以及实际观察到的特点。
3. **适配**：如何用于当前项目，关键差异与必要依赖。
4. **证据边界**：只说明会影响结论的未核实或未运行项。

比较时可用：

| 具体参考 | 为什么适合 | 当前项目怎么用 | 重要限制 |
| --- | --- | --- | --- |
| 实际访问的组件/示例链接 | 与任务有关的依据 | 现有组件改造/源码改编/模式借鉴 | 实际存在的限制 |

不把“我喜欢”“更高级”“组件更多”当成充分理由。把审美判断连到信息层级、操作路径或产品语境。
用户要全部来源时按分类提供目录，不继承上游强制只返回固定数量的限制。

## 详细交接

仅在用户要求详细设计、多页面方案或交给其他实现者时使用。

- **上下文**：页面用途、主要操作、技术栈、现有设计约束、明确假设。
- **选型**：选中和放弃的关键候选及理由；没有真实比较就不编造淘汰过程。
- **区域映射**：每个关键区域采用哪个具体模式、组件或来源。
- **适配决策**：布局、密度、样式变量、动效、相关状态和依赖变化；说明哪些任务约束决定了选择，新增依赖相对现有方案带来什么收益。
- **实现路径**：使用本地组件、改编源码或重实现交互；源码来源、版本和许可依据。
- **验收点**：与改动相关的响应式、交互、焦点、状态转换、代表性数据及项目检查；仅在已获授权实现时执行，不为每个组件列全套状态。
- **证据**：访问日期；分别描述文档、视觉、演示操作、源码和项目运行证据。

沿用项目现有文档位置和格式。只有需要保存交付时写文件；不要同时生成多份重复设计文档。

## 示例：现有 Ant Design 业务后台

以下是说明输出结构的假设场景，不是真实调研记录，不可据此声称已经查看文档或运行页面。

假设：项目已经使用 Ant Design，用户希望改善订单表格上方的筛选区，只要求方案。

合适的决策方向：保留 Ant Design 的 Table 和表单控件，把常用筛选保留在首行，低频条件折叠；批量操作随选中状态出现；使用项目现有间距与主题。应查该项目版本对应的 Table、Form 等官方示例并给出真正访问的链接。

若只查到 API 文档：给出技术方案，说明尚未观察实际视觉和交互效果。
若看过官方演示：描述真实观察到的状态，仍不要宣称当前项目已经有效运行。
在用户要求实现后再修改代码和验证；用户已经要求“调研后直接实现”时则持续完成任务。

## 常见表达修正

| 没有足够依据的说法 | 根据实际证据表达 |
| --- | --- |
| “看过文档，这个动效很流畅” | “文档提供了动画用法，流畅度尚未观察” |
| “源码是 MIT，所以所有素材都能复制” | “代码许可已查；所用图标/字体/图片按各自条件核实” |
| “原站能运行，项目已验证” | “原站演示已操作；项目内尚未验证” |
| “首页打不开，组件库不存在” | “当前入口访问失败；继续查官方文档或仓库” |
